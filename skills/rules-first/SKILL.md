# 先定规则，再动手

先把规则写清楚，再按用户审核的方案，一次完成用户指定的一项任务，最后用证据验收。适用于新建和修改数据分析工具、自动化脚本及已有工具。

## 不可跳过的约定

- 严格按 **Specify → Plan 评审 → Implement → Validate** 推进。续接已审核项目时核对已有记录，从实际阶段继续，不重复索要仍有效的确认。
- AI 整理资料、提出技术方案；用户决定业务规则、禁止事项和验收口径。资料未说明的业务规则必须列为待确认，不能把推测写成已定规则。
- **确认标准**后才能进入架构评审；**方案通过、任务与方案一致、用户明确指定本次执行任务**后才能编码。沉默、等待时间、AI 自查通过都不等于用户批准。
- 一次只实现一项明确指定的任务。可以记录下一项待办，但不能自动开始。已有明确指定且仍有效的任务授权不用重复确认。
- 已确认的 `spec.md` 与 `constitution.md` 是恢复和验收依据。二者冲突时不能自行选一条执行；先列出冲突让用户决定。记忆、旧实现、测试结果和临时方案都不能覆盖已确认规则。
- 代码与确认规则冲突时改代码、重跑检查；禁止为了通过检查而放宽需求、改阈值、改等号归属或降低验收标准。
- 未实际执行的检查写“未验证”，失败写“未通过”，不能把计划、推测或没有报错写成“通过”。

## 文档落点与状态

先定位用户正在操作的项目。默认将 `spec.md`、`plan.md`、`tasks.md`、`constitution.md`、`MEMORY.md` 放在项目根目录。若项目已经有这套文档，沿用其位置，在记忆中记录路径，避免创建两套相互矛盾的规则。

每次写文件前先读取同名文件，保留有效规则、历史结论、任务编号和验收证据，进行有针对性的更新。四份文档必须真实落盘，不能只在聊天里展示。不要用模板覆盖已有项目文档。

首次建立文档时使用以下模板，按项目实际情况填充；模板里的 `〈…〉` 是填写提示，不是已确定规则：

- [spec.md](assets/templates/spec.md)：需求、数据规则、验收条件、待确认问题和确认记录。
- [plan.md](assets/templates/plan.md)：三层分工、数据流、隔离边界、自查与用户评审记录。
- [tasks.md](assets/templates/tasks.md)：依赖明确的小任务、执行结果及逐条验收证据。
- [constitution.md](assets/templates/constitution.md)：可检查的项目强制规范。
- [MEMORY.md](assets/templates/MEMORY.md)：阶段、任务、经验和恢复入口。

四份文档都标明“草稿”或“已确认”、版本、更新时间、已确认范围和确认依据；正文分开写“已定规则”和“待定问题/提案”。没有用户确认依据的内容保持草稿。初次 Specify 时创建四份草稿；最迟在第一次 `topic-open` 前建立初始 `MEMORY.md`，说明尚未实施。

只在用户明确确认后更新对应状态。记录确认的版本/条款、用户原意、日期和仍待定的问题，不能伪造确认。部分确认须标清范围，含未确认提案的整份文档仍标“草稿”。执行结果的追加不自动推翻已确认的任务定义；修改已确认内容则保留旧依据，将受影响部分标为草稿/待复审。

每一步结束都先保存对应文档，再用大白话说明：

1. **现在到哪了**：当前阶段、任务编号、已做和未做的事。
2. **已经存在哪**：给出文件链接和具体条款/任务/验收编号。
3. **需要你看什么**：列出需要决定的规则或需要复核的结果，避免只说“请审核”。
4. **下一步要满足什么**：明确哪些确认或检查还没完成；条件满足就按授权继续。

## 1. Specify｜先确认标准

读取现有项目文档、相关代码、样例数据和用户提供的资料。已有行为只是调查依据，不自动成为已确认需求。先完成能确定的内容，不因个别缺项而只提问、不落盘。

实际创建或更新四份草稿：

- `spec.md`：写明目标、范围和禁止事项、输入/输出（格式、单位、有效范围等）、数据处理规则、异常处理。每条关键需求用稳定编号 `REQ-001` 等，并给出能实际核对的验收条件，包含必要的边界、无效输入和错误场景。业务禁止事项也要编号。
- `plan.md`：提出恰好三层的职责划分、数据传递方式、调用边界和隔离要求。已有项目明确拟修改的文件/模块、现有职责、预期变化及受影响功能。此时是待评审提案。
- `tasks.md`：拆成可以独立实现和验证的小任务。每项包含任务编号、对应需求、前置任务、改动范围、完成标志、检查方法；不能把“实现全部功能”当作一个任务。
- `constitution.md`：按代码、目录、依赖、数据文件、错误处理和检查六类写强制规范；家规用 `RULE-001` 等编号，每条尽量给出检查方法。新规范在用户确认前只是提案，不自行标为已生效。

待定问题用 `Q-001` 等编号，写清来源缺口、可选处理、影响的需求/任务及是否阻塞确认标准。数据阈值、等号归属、边缘处理、无效像素等缺失时不得自行填值。必要的技术建议可写入提案，与业务定论分开。

**确认标准关口：** 四份草稿齐备，用户已确认关键需求、业务禁止事项、验收口径和家规，且没有影响这些标准的未决问题，才能进入 Plan 评审。确认结果写回 `spec.md`、`constitution.md` 及相关文档；其余未决事项保持可见。未过关时可继续整理文档，不能编码。

## 2. Plan 评审｜先检查三层分工

先对照已确认的 `spec.md` 和 `constitution.md` 自查 `plan.md`，把结果和依据条款记入 `plan.md`。检查：

- 三层各自负责什么、不负责什么；有没有遗漏职责、重复职责或循环依赖。
- 数据从哪个入口进入，每一步的结构、单位、校验责任和输出是什么；结果怎样返回或保存。
- 每层允许调用哪些层/接口，是否把文件读写、纯业务规则、界面/流程控制混在一起。
- 哪些功能必须隔离；已有项目的改动位置、接口变化和回归影响是否明确。
- 每项任务是否能追溯到需求、对应方案模块，并有独立完成标志与检查方法。

三层的名称与设计以项目实际情况和用户审核为准。没有现成结构时，可提出“入口与流程层、业务规则层、数据与外部服务适配层”：入口编排调用；业务层处理纯计算和判定；适配层承担文件/服务交互。明确调用接口和返回的数据，业务层不直接依赖具体存储或界面。这只是起草方案的技术建议，不能冒充用户已批准的架构。

对于小麦施肥项目，读取 [小麦施肥评审与验收](references/wheat-fertilization.md)，重点审查训练和业务运行隔离，并明确像素聚合、施肥分级各属哪一层。不要将这一领域的规则套用到其他项目。

发现不合理分工时，直接修订 `plan.md`，同步调整受影响的 `tasks.md`，写明“原来怎样、改成怎样、为什么、影响哪些需求和任务”。修订后的方案重新提交审核，不能凭旧版本的批准开始执行新方案。

**编码关口：** 用户审核通过当前方案；任务清单与当前方案一致；用户明确指定本次任务编号或能唯一对应到某个任务的工作；前置任务已满足。记录这些依据后才能进入 Implement。只收到“方案通过”但没指定任务时，说明候选任务并等待指定；不要擅自选一个开工。用户已指定且关口满足时直接执行。

## 3. Implement｜一次一项，读规则再动手

`topic-open` 和 `topic-save` 是本 Skill 内的操作指令，不是独立 Skill 或系统 shell 命令。用户直接输入这两个指令时，执行对应操作。

### `topic-open`｜读项目规则

新对话接续项目或开始每项任务前：

1. 完整读取 `spec.md`、`plan.md`、`tasks.md`、`constitution.md`、`MEMORY.md`，核对版本、确认依据、任务状态和实际文件。不能只依赖上次聊天或记忆摘要。
2. 先报告本次任务编号、改动范围、直接相关的 `REQ-*`/`RULE-*`、禁止事项、计划执行的检查及前置条件。没有指定任务就写“本次尚未指定执行任务”，不猜测任务。
3. 关键文档缺失、不可读、规则冲突、方案未通过或前置任务未满足时，说明具体文件/条款、影响和解决办法，先解决再编码。可以修复路径或补起草缺失文档，但不能自行补审批。
4. 如果只是新项目首次建立记忆，可据已读文档创建 `MEMORY.md`，标明此前无记忆可恢复。已有项目记忆丢失时先核对任务和代码，重建有依据的状态，无法确认的历史明确写“未知”。

单独的 `topic-open` 只读取、整理和汇报，不自动授权实现。若用户同时明确指定任务，则在所有关口满足后继续。

### 实现当前任务

- 只改动当前任务约定范围，以及完成它所必需、已在方案和任务范围中的内容。遇到其他问题记入待办，不顺手实现下一项。
- 保持需求编号和任务编号可追踪；实际改动、运行的检查、真实结果和任务状态写回 `tasks.md`。
- 需要改变已审核架构时停止受影响的编码，回到 Plan 评审，先修订方案和任务并重新审核。
- 发现规格矛盾或缺项时列出具体条款、影响和选项，回到 Specify 请用户决定；同步更新方案和任务，重过受影响的关口后再恢复。
- 完成改动后进入下面的 Validate，验收后执行 `topic-save`。未通过、未验证、阻塞或中断也要保存真实进度，不能冒记完成。

### `topic-save`｜保存进度和经验

每项任务结束后，或用户明确要求时，先读取再更新 `MEMORY.md`，记录：

- 当前阶段、文档版本和已获得的确认；本次任务完成情况与证据位置。
- 发现的问题、根因（未知就写未知）、解决办法及检查结果。
- 未解决事项、阻塞原因、下一项待办及其是否已获执行授权。
- 涉及业务规则时引用 `spec.md` 中的 `REQ-*`，不把新推测写成规则；规范相关内容引用 `RULE-*`。
- 恢复时应该先读哪些文件、看哪些条款、跑什么检查。

同步更新 `tasks.md` 的状态，保证记忆与任务清单一致。明确区分“实现已完成”和“验收已通过”。`topic-save` 不触发新任务；下次恢复以已确认规格和家规为准。

## 4. Validate｜逐条用证据校验

每项任务完成后，按其关联的需求编号逐条核对，并检查受影响的既有功能和相关家规。全部任务完成后，再对全部关键需求、禁止事项、架构和家规做一次整体校验，不能仅把各任务的通过记录拼在一起冒充整体运行。

每次校验都把结果写入 `tasks.md` 的验收区。每项至少记录：

| 字段 | 填写要求 |
| --- | --- |
| 验收编号与范围 | 如 `VAL-001`；对应 `T-001` 或“整体校验” |
| 需求/家规编号 | 指向 `spec.md`、`constitution.md` 的具体条款及版本，架构检查注明 `plan.md` 小节 |
| 预期结果 | 依据已确认规则写出可对比的结果，不能事后按实际结果倒填 |
| 检查依据 | 样例输入、数据/模型/环境版本、执行命令或人工步骤，以及日志/报告/输出文件位置；按需要记录，不泄露凭据 |
| 实际结果 | 实测值、输出行为或具体错误；未运行则说明原因和补验办法 |
| 状态 | 仅用“通过”“未通过”“未验证” |

可手工核对、运行命令或使用自动化检查，采用能证明要求的方法。数值容差需要有已确认依据，不能为了消除失败临时放宽。检查失败就修正代码并重跑相关项，把失败和复验事实都留下；依赖不可用或条件不足就标“未验证”。所有必需检查通过后才将任务标为“已完成”，仍有未验证时写“待验证”。

**用证据验收关口：** 代码必须服从已确认规格。若规格本身矛盾或缺项，列出条款、影响和待用户决策事项，用户决定修改后再同步更新方案/任务和检查，不自行降低标准。用户人工复核情况单独记录，不能用 AI 测试通过代替用户验收。

最后用大白话报告通过/未通过/未验证的数量和限制，明确让用户打开哪个文件、看哪个任务及哪条验收记录复核。任务结束保存 `MEMORY.md`，等待下一项明确授权。
